# Scroll-Site Generator

Turn a product brief into a cinematic scroll-driven website: a product film
scrubbed by scroll position (the technique behind Apple's AirPods pages),
with huge typography, chapter captions and a premium dark aesthetic.

Proven reference builds live in `~/test saas/`: `coffee-scroll` (AURUM One),
`camera-scroll` (OBSCURA M) — both vanilla — and `nova-x1` (GSAP/Next.js).

## What the user gives you

A product (real or fictional) and optionally: scroll beats ("lens elements
float apart, sensor appears..."), a vibe ("matte black + brass"), a brand
name, and a tech-stack preference. Everything missing, you invent tastefully.
If no aesthetic is given, default to: near-black background (#050505-#0a0a0c),
one accent color that suits the product, huge tight-tracked display type,
generous negative space.

## Choose the architecture

- **Vanilla scroll-film** (default): one continuous film sliced into ~400
  WebP frames, scrubbed on a canvas. Best when the brief is a list of
  cinematic beats. Zero build step, deploys anywhere.
  → read `references/vanilla-film.md`
- **GSAP/Next.js hybrid**: pinned sections mixing frame-scrubbed canvases with
  pure GSAP animation (exploded layers, energy pulses, particles, morphs).
  Choose when the brief asks for GSAP/React/sections/labels/specs or reads
  like a marketing-page spec rather than a single film.
  → read `references/gsap-nextjs.md`

## Generation model: Google Flow has no API — this is a manual handoff

There is no scriptable way to generate stills or clips. Flow (flow.google)
is a browser-only tool with no public generation API, so every image and
video in this pipeline is generated by **the user**, by hand, in Flow's UI.
Your job is to write the prompt, not submit it. Concretely, for every still
or clip the pipeline needs:

1. Write a complete, ready-to-paste prompt (see `references/prompts.md` for
   the recipes and conventions) — specify exactly what model/mode within
   Flow to use (Nano Banana for stills, Veo 3.1 image-to-video for clips),
   the full prompt text, and — for clips — which still or frame to use as
   the starting image.
2. Present it clearly and **stop working** — do not proceed to the next
   chapter, do not assume a result, do not simulate or invent output. Tell
   the user what file name/path to save the download as (matching the
   project's expected layout) and wait.
3. When the user returns with the file (uploaded here, or a path if they're
   working locally), pick the pipeline back up: QC it, patch it if needed,
   move to the next prompt.

Never batch every chapter's prompt into one wall of text and call it done —
give one prompt at a time (or a small logical group, e.g. the 2-3 hero
candidates), wait for that result, and let it inform the next prompt (e.g.
a chapter clip's prompt needs to name the hero's actual details once you've
seen it). Treat each halt as a real stop, not a formality.

## Pipeline (both architectures)

1. **Storyboard.** Map the brief onto 5-8 chapters, each one visual idea.
   Decide per chapter: video clip, still + GSAP trick, or pure CSS/GSAP.
2. **Hero still first.** Write 1-3 candidate prompts for Flow's still
   generator (Nano Banana), following `references/prompts.md`. Present them
   and halt. The hero anchors every video clip — once the user returns with
   candidates, let them pick if they're around; otherwise pick the most
   consistent/symmetric one and say so. Patch text artifacts with Pillow
   before the user spends any video generations on it (AI stills love fake
   logos — clone/gradient-fill them out; check zoomed crops).
3. **Chapter clips** via Flow's Veo 3.1 image-to-video, anchored for
   consistency (this is the anti-morphing system):
   - Every clip that shows the product should start from the hero or from
     another clip's extracted last frame (`ffmpeg -sseof -0.1 ...
     -frames:v 1`) — write the prompt naming that starting image and tell
     the user which file to feed Flow as the input frame. Chain state
     changes (cup fills → milk in).
   - "Product assembles itself": write a prompt for a *disassembly/
     explosion* from the hero, explicit about the end state, meant to be
     played REVERSED once downloaded — it then ends pixel-perfect on the
     hero. Reversing it is your job (`ffmpeg -vf reverse`), not the user's.
   - One prompt/halt per clip (or small batch) — never assume a clip
     succeeded. When the file comes back, QC it with an ffmpeg contact
     sheet (first/quarter/mid/three-quarter/last frames) before using it.
     If it failed (morphing, duplication, wrong action), rewrite just that
     prompt and send the user back to regenerate — never the whole set.
   - Prompt recipes and known failure modes: `references/prompts.md`.
4. **Build frames.** `scripts/build_master.py` xfade-concats the chapters,
   slices ~12fps 1400px WebP frames (~15-25 MB total) and prints per-chapter
   scroll fractions — use those to place captions. For standalone sequences
   (a 360° rotation for a GSAP section) use `scripts/extract.py`.
5. **Site.** Copy the engine from `assets/` (see the architecture reference),
   rebrand colors/copy, calibrate captions to the printed fractions.
6. **The full brand page.** The film is only the opening act — a run that
   ends at the film has built a fancy header, not a website. Continue the
   scroll below the film with a complete brand homepage (manifesto, origin
   story, craft chapters, stats, specs, quotes, gallery, closing CTA,
   sticky nav, real footer), told as one continuous brand story in the same
   design system. This normally costs zero extra generations — it reuses
   crops and rejects. → read `references/brand-page.md` and use
   `assets/brand-sections.html`.
7. **Verify.** No claude-in-chrome available (free-tier account) — see
   "Verification gotchas" for the fallback approach: preview-panel pixel
   probes plus asking the user to do a manual scroll-through before calling
   it done.
8. **Host.** Add a launch.json config (next free port: check existing ones in
   `~/test saas/.claude/launch.json`), serve with `python3 -m http.server`
   (vanilla) or `next dev` (hybrid), `open` it in the browser. Offer GitHub
   Pages deploy → `references/deploy.md`.

## Failure modes (learned the hard way, on Kling — verify against Veo 3.1)

These were observed on the previous Kling-based pipeline. Veo 3.1 may not
share every failure mode — treat these as things to watch for, not settled
fact, until confirmed on a shipped Flow-based site:

- **Complex multi-part objects may duplicate** (sneakers became two shoes)
  instead of separating layers, on Kling. If an explosion/exploded-view clip
  fails twice: generate the exploded state as a *still* instead (image
  models are excellent at these), slice it into contiguous horizontal
  strips with Pillow, and animate the strips apart with GSAP/CSS
  transforms. Looks better anyway, and sidesteps the video model entirely.
- **Chapter cuts reset object state** (full cup → empty cup). Mask with the
  0.4s crossfades build_master adds, and land captions near cuts.
- Local ffmpeg has **no WebP encoder** — extract PNG, convert with Pillow
  (the bundled scripts already do this).
- Still images sit in visible rectangles on the page. Blend with a radial
  `mask-image` (`.img-blend` pattern) and fade strip edges horizontally.
- Caption with `data-in="0.00"` is invisible at exactly scroll 0 — give the
  opening title a negative data-in.

## Verification gotchas

No claude-in-chrome on a free-tier account, so real-browser scroll/
screenshot verification isn't available directly. Fall back to:
- **Vanilla sites**: the Launch preview panel's pixel/element probes
  (reading canvas pixels via `preview_eval`) are reliable enough — the
  panel's `hidden` tab issue (rAF suspends, screenshots desync from canvas
  compositing) mainly affects GSAP tickers, less the static-frame canvas
  scrubber. Screenshot twice if unsure.
- **GSAP/Next.js hybrid sites**: the preview panel's hidden-tab problem
  hits these harder (stalled tickers, desynced screenshots). Ask the user
  to run `next dev` locally, open it in their own browser, and manually
  scroll through — call out specifically what to check (every chapter
  transition, captions, mobile viewport, and the below-film sections: nav
  appears after the film, reveal animations fire, footer present).
- Remember GitHub Pages caches HTML for ~10 min after a redeploy —
  cache-bust with `?fresh=1` if verifying a live deploy right after pushing.
